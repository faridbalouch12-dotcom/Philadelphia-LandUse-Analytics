Lookup Table vs. SCD Type 2 vs. Crosswalk

Three patterns, three problems, three layers — with concrete examples from the Philly zoning warehouse

Lookup Table
dim_zoning_code
Warehouse · Dimension layer
Entity: the zoning code Static reference

Problem it solves: You need a stable reference for all known zoning codes so fact tables can join to a description without duplicating it everywhere.

When to use: The entity's identity and descriptive attributes are stable — there's nothing to track over time.

Key behavior: Retired codes stay with active = FALSE. New confirmed classifications get INSERTed. No history rows needed.

SCD Type 2
dim_zoning_code (versioned)
Warehouse · Dimension layer
Entity: the zoning code History-tracking

Problem it solves: A code's descriptive attributes change over time and you need to know what the description was at a specific point in time when a fact row was recorded.

When to use: A confirmed ordinance amendment changes what a code means (e.g., RSA-5 now allows 5 stories instead of 3). Not yet triggered in our project.

Key behavior: Surrogate key + effective_date + expiry_date + current_row flag. Fact rows join to the right dimension version via date.

Crosswalk Table
stg_zoning_code_crosswalk
Pipeline · Staging layer
Entity: a (source, canonical) mapping Normalization

Problem it solves: A source code label in a vintage shapefile differs from the canonical code stored in the warehouse — but refers to the same thing (confirmed rename).

When to use: A rename is confirmed via spatial overlap check or official documentation. Never for unconfirmed cases.

Key behavior: Maps source_code + vintage_year → canonical_code. Lives in staging, not warehouse. Never tracks history — it's a normalization step.

The three scenarios when a code appears or disappears between vintages

Scenario A — Code Stable
What happened: RSA-5 appears in both 2022 and 2023 shapefiles with the same meaning.

String comparison result: No flag. Code present in both years.

Spatial check needed? No.
Action: No crosswalk row needed. Fact rows join dim_zoning_code normally.
Scenario B — Rename
What happened: RSA-5A in 2021 was renamed RSA-5 in 2022. Same land, different label. City documented the rename.

String comparison result: RSA-5A disappears; RSA-5 appears. Flagged as candidate rename.

Spatial check result: 98% polygon overlap confirms same geography.
Action: Add crosswalk row (RSA-5A, 2021 → RSA-5). No new dim_zoning_code row needed.
Scenario C — New Classification
What happened: RSA-6 appears in 2023 for the first time. City created a new density category for small attached row homes.

String comparison result: RSA-6 appears with no prior year match. Flagged.

Spatial check result: Low overlap with any prior code — genuinely new.
Action: INSERT RSA-6 into dim_zoning_code. No crosswalk row. Tag affected fact rows vocab_stable=FALSE.

Why this matters for analytics — the SCD Type 2 problem illustrated

Without SCD Type 2, a user filtering on RSA-5 and comparing pct_district_area across years gets a misleading result if the definition changed. Here's the concrete example.

Without SCD Type 2 (static lookup)

User runs a query: "Show me RSA-5 area share in District 7, 2021 vs. 2024."

SELECT year, pct_district_area
FROM fct_district_year_zoning
JOIN dim_zoning_code USING (zoning_code_id)
WHERE long_code = 'RSA-5'
AND district_id = 7

Result: 2021 → 42%, 2024 → 47%

Problem: The user concludes District 7 gained 5% more RSA-5 land. But if RSA-5's definition changed in 2023 (now allows 5 stories), the comparison is between two different regulatory categories wearing the same label. The "gain" may reflect reclassification under the new definition, not actual rezoning.

With SCD Type 2 (versioned dimension)

Same query, but fact rows join to the correct dimension version via date:

SELECT f.year, f.pct_district_area,
d.max_stories, d.effective_date
FROM fct_district_year_zoning f
JOIN dim_zoning_code d
ON f.zoning_code_sk = d.zoning_code_sk
WHERE d.long_code = 'RSA-5'
AND f.district_id = 7

Result: 2021 → 42% (RSA-5 v1, max 3 stories), 2024 → 47% (RSA-5 v2, max 5 stories)

Correct behavior: The user sees that they're comparing two different versions of RSA-5. The dashboard can surface a warning: "Note: RSA-5 definition changed on 2023-06-15." The comparison is now interpretable.

The decision rule for our project: Use a lookup table until a confirmed ordinance amendment changes a code's meaning — then upgrade to SCD Type 2. Use the crosswalk in the pipeline whenever a confirmed rename maps a source code to its canonical warehouse equivalent. These three patterns solve different problems at different layers and should never be conflated.
