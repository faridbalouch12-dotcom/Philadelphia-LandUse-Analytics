## Key concepts discussed

### Blast radius as the core design challenge
Farid identified that the hardest part wasn't deciding how many reset levels to have — it was figuring out what each level should and shouldn't touch. This is the real engineering judgment: getting the blast radius wrong means either destroying too much (wasting time re-ingesting from APIs) or too little (the reset doesn't actually fix the problem).

### Escalating reset levels — smallest fix first
The four-level model mirrors how production reset workflows are structured:
1. **analytics** — just the output layer; raw through marts are trusted
2. **transforms** — dbt-managed schemas (intermediate, marts, analytics); raw is trusted
3. **data** — all five schemas; re-ingest from APIs
4. **nuclear** — destroy the Docker volume entirely; infrastructure-level fix

The "Rule of thumb: Use the smallest reset that fixes the problem" is the safety principle that ties it together.

### What is NOT reset — the negative space matters
The "What is NOT reset" table is the kind of documentation most runbooks forget. Farid explicitly listed `.env`, code files, `metabase_data` volume, and git history. This forces the reader to think about what's safe before running a destructive command.

### Quick-reference decision table
The failure-mode-to-command mapping at the top of the runbook is immediately useful — you don't have to read the full doc to pick the right reset level. This is good runbook design: answer "what do I run?" before explaining "why."

## How these concepts connect

The reset workflow depends directly on the schema architecture from Tasks 25.1–25.3. The five schemas (`raw`, `staging`, `intermediate`, `marts`, `analytics`) and the write-access policy determine which reset levels are possible — you can only drop `intermediate` + `marts` + `analytics` independently because dbt owns those layers and can rebuild them from `raw`.

The Makefile targets will be exercised constantly during the vertical slice work (Weeks 6–9). Every time a dbt model breaks or raw data needs refreshing, these commands are the recovery path. The `reset-nuclear` target is the equivalent of the stack smoke test (Task 24.5) — it validates the full bootstrap chain from scratch.
