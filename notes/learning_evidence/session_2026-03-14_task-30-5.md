## Key Concepts Discussed

### Syllabus as Roadmap (Meta)
Big session-level decision: the syllabus is a guide, not a contract. Created `/adjust-task` skill and CLAUDE.md sections for Syllabus Flexibility and Analytical Rigor. When implementation diverges from tasks, we update the syllabus — not fight the learner.

### Direct-to-PostGIS Architecture
Skipped local file snapshots entirely. Python extractor loads via `to_postgis()` straight into the `raw` schema. Traceability handled by `raw.ingestion_logs` instead of local manifest.json files. Tradeoffs discussed: no offline inspection, must re-hit API on rebuild — acceptable for 18 static rows.

### Python Module Execution Model
- Top-level code runs on import — `import planning_districts` would trigger the full API call
- `if __name__ == "__main__":` pattern separates "define" from "execute"
- Relative imports (`from . import utils`) require `python -m` to run
- Functions as the unit of work, `__main__` as the intentional entry point

### Error Handling: raise vs. silent None
`except: print()` without `raise` returns `None` silently. Callers get confusing downstream errors instead of a clear failure. Only catch when you can recover.

### Postgres DEFAULT NOW()
No need to pass timestamps from Python — `DEFAULT NOW()` in the DDL handles it at insert time. Store the raw timestamp, derive "days since" at query time.

### Preventive vs Validation Testing
- **Preventive (pre-load):** Stop bad data before it enters. Use when bad loads are expensive to undo.
- **Validation (post-load):** Verify state is correct after load/transform. Use when transformation is the risk, not the load itself.
- At scale, use both: preventive guards the boundary, validation guards the output.
- For this project: validation sufficient for 18 static districts. Preventive becomes important for permits.

### Data Fix Strategies
Three approaches when data is wrong:
1. **Fix & full rebuild** — fix root cause, `make reset-data`. Always preferred.
2. **Targeted backfill** — reprocess only the bad partition. Requires pipeline support for parameterized runs.
3. **Manual patch** — ad-hoc UPDATE. Last resort, bypasses all validation and lineage.
Principle: if the pipeline produced wrong output, fix the pipeline. Data should always be reproducible from source.

### dbt generate_schema_name Macro
Default dbt behavior: `{target_schema}_{custom_schema}` → `staging_staging`. Override with a custom macro that returns just the custom schema name. One of those dbt gotchas not obvious from docs.

### Shape__Area Mystery
Source `Shape__Area` value (48,752,522) doesn't map cleanly to square feet, meters, or any obvious unit. Confirmed the Month 1 decision to ignore it and derive `land_area_sqmi` from geometry instead.

### ST_Transform in PostGIS
- Positional args: `ST_Transform(geometry, target_srid)` — no named parameters
- PostGIS knows the source SRID from the geometry column, no need to specify `from_proj`
- EPSG:2272 (PA State Plane South) uses feet; 1 sq mi = 27,878,400 sq ft

### Quoting Mixed-Case Columns in Postgres
`to_postgis()` preserves original case. Postgres folds unquoted identifiers to lowercase. Must use `pd."Shape__Area"` to reference mixed-case columns.

### No Semicolons in dbt Models
dbt wraps SQL in `CREATE VIEW ... AS (...)`. A trailing semicolon breaks the wrapper statement.
