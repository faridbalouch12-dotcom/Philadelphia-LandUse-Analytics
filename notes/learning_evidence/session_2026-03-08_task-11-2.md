## Key concepts and decisions

**ERD vs star schema:** Clarified early — ERD is a notation tool, not a design pattern. Star schema is the Kimball dimensional modeling pattern. The ERD just draws what the star schema already decided.

**9 entities identified:** 3 dimensions, 3 facts, 1 bridge, 1 aggregation, 1 feature layer. The 7th+ entities (geo_district_boundaries, bridge, agg) emerged during the entity-by-entity discussion rather than being listed upfront.

**Geometry separation (DD2):** the learner initially put polygon geometry in `dim_district`. Through discussion about storage overhead and join performance, decided to split geometry into a separate `geo_district_boundaries` (E8). Analytics joins to `dim_district` stay lightweight; geometry loaded only when needed.

**EOY date pattern (DD1):** the learner proposed joining `fct_district_year_zoning_composition` to `dim_date` on year integer. Identified as fan-out problem (365 rows per fact row per year). Solution: add `vintage_date` as an EOY surrogate date column (e.g., `2023-12-31`). This gives a clean 1:1 join to `dim_date`. Same pattern applied to `acs_period_end_date` and `boundary_version_eoy`.

**Fact-as-lookup (DD3):** Bridge needs to reference census tracts. the learner initially proposed renaming `fct_tract_acs` to `dim_tract_acs`. Discussion surfaced that ACS data contains measurements (estimates + MOE), not purely descriptive attributes. A `dim_` table that stores numeric measures would be architecturally confusing. Decision: keep `fct_` prefix, document the fact-as-lookup pattern explicitly.

**Data-derived bins (DD4):** the learner proposed a `dim_attribute_bin` lookup table for histogram bins. Problem: bins are computed from percentiles of `fct_tract_acs` at pipeline time — they're data-derived, not predefined. A static lookup can't represent data-derived values. Decision: `census_attribute` and `bin_range` stored as inline string columns on the aggregation table.

**YoY change not stored (DD5):** YoY zoning change is computed at query time via self-join or window function. Storing it would mix snapshot and change facts in the same table (FM2 from Task 11.1).
