## Key concepts discussed

### Separation of duties by schema layer
The core design question was: which component is the sole writer to each schema? Farid arrived at this quickly — the principle of "each component isolated to its own schema" was intuitive. The hard part was articulating it precisely as a policy rather than a vague rule.

### Python vs. dbt: where does each tool live?
This generated a good detour. Farid asked whether Python could be used for transformations in staging/intermediate (he has DuckDB experience and likes the DataFrame-style flexibility). We worked through two options:
- **Option A:** Python writes transformed results to `staging` directly
- **Option B:** Python preprocesses and writes back to `raw`; dbt reads from there and writes to `staging`

He rejected `raw_processed` as a separate schema (correctly — it would just be another warehouse layer). Settled on raw table naming convention (`raw.permits_li_processed` vs `raw.permits_li`) if Python preprocessing is ever needed within raw. Ultimately decided: **Python is scoped to `raw` only; dbt owns `staging` onward.**

### What dbt actually does (vs. DuckDB/Databricks)
Farid asked why dbt is popular when Python can do everything it does. Clarified:
- dbt is SQL-only, database-in/database-out — no file I/O, no DataFrames
- No handoff mechanism between Python objects and dbt models
- The Python pipeline writes to DB; dbt reads from DB — no in-memory sharing

After the task was graded, the "why is dbt popular" question got a full answer. Key points:

**Why not pure Python for transforms?**
- pandas/polars pull data into memory — breaks at scale; SQL runs in-DB where the data lives
- Python transform pipelines have no built-in dependency management — you'd have to wire Airflow/Prefect yourself; dbt's `ref()` gives you a DAG for free
- Python pipelines tend toward spaghetti with no enforced structure

**Why not stored procedures?**
- Live in the database, not the repo — can't diff, PR-review, or `git blame` them
- Vendor-specific syntax — Postgres ≠ Snowflake ≠ BigQuery; dbt abstracts this
- No lineage, no docs generation, no selective re-runs

**What dbt actually adds over raw SQL:**
- Automatic DAG from `ref()` — builds in dependency order, re-runs only what changed
- Built-in testing via YAML schema tests (`not_null`, `unique`, `relationships`)
- `dbt docs generate` creates a browsable lineage/docs site automatically
- Idempotency by default — re-running produces the same result
- Materialization strategy configurable per layer (view, table, incremental)

**Where DuckDB fits:**
DuckDB is an engine, not a dbt competitor. `dbt-duckdb` is a real adapter — you can use dbt's discipline layer on top of DuckDB's speed. They're complementary, not alternatives.

**The Python + dbt split in one sentence:**
Python does what SQL can't (HTTP, file I/O, ML, geocoding APIs); dbt does what Python shouldn't (in-DB transforms with lineage, testing, and docs baked in).

### Convention vs. Postgres role enforcement
Explicitly documented that this is a convention enforced by code discipline, not by separate Postgres users/roles. The single-developer context makes role-level enforcement overkill, but the policy still matters to prevent accidental layer leakage as the pipeline grows.

## Post-grade policy revision — `analytics` dual-writer exception

After grading, the policy was revised. The `agg_district_acs_attributes` discussion surfaced a real edge case: weighted tract-to-district aggregations + binning is complex enough that Python's intermediate state inspection is a genuine advantage over a multi-level SQL CTE.

**Decision:** `analytics` is now a dual-writer schema — dbt `agg_*` as default, Python pipeline as a permitted exception when:
1. The transformation requires intermediate state inspection during development
2. The SQL equivalent would be materially harder to read, test, and debug

**Guardrail added:** Python-written tables in `analytics` must still use `agg_` prefix naming and full documentation — the exception doesn't waive documentation requirements.

**Also discussed:** Multi-database vs. multi-schema architecture (medallion pattern). Single Postgres instance with schemas is the right call for local dev — cross-database queries in Postgres require `dblink`/`fdw` extensions, and dbt's `ref()` doesn't handle them natively. The schema-per-layer approach gives enough separation without the infrastructure complexity.
