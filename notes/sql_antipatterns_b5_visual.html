The Shared Root Cause

Both antipatterns are the same mistake in different clothes: a data value leaks into the schema and becomes a structural object. When the data changes, the schema has to change too — and schema changes are expensive, risky, and often disruptive.

Data values
year, category, status
— should live as rows
→
Become schema objects
table names, column names,
ENUM values, CHECK constraints
→
Schema must change
when data changes
DDL ops, downtime, ETL,
broken pipelines
"Use metadata when validating against a fixed set of values.
Use data when validating against a fluid set of values."
— Bill Karwin, SQL Antipatterns Ch. 11, p. 138

Chapter 9 — Metadata Tribbles Antipattern

Objective: improve performance by keeping tables small. Mistaken approach: split one table into many using a data value (year, category) as the split key.

Form 1: Spawning Tables

✗ Antipattern — Table per year

CREATE TABLE Permits_2021 ( ... );
CREATE TABLE Permits_2022 ( ... );
CREATE TABLE Permits_2023 ( ... );
-- January 2024: pipeline fails.
-- Permits_2024 doesn't exist yet.
Schema changes when data changes FK impossible — which table? UNION grows every year Update anomaly on date correction

✓ Solution — One table, year is a value

CREATE TABLE Permits (
    permit_id   SERIAL PRIMARY KEY,
    permittype  TEXT,
    issue_date  DATE,   -- year extracted here
    district_id INT
);

-- Year is just EXTRACT(YEAR FROM issue_date)
-- No new table needed. Ever.
One FK target for all dependents Date correction = simple UPDATE New year = zero schema change

Form 2: Spawning Columns

✗ Antipattern — Column per year

CREATE TABLE DistrictMetrics (
    district_id        INT,
    permit_count_2021  INT,
    permit_count_2022  INT,
    permit_count_2023  INT
    -- ALTER TABLE every January
);
ALTER TABLE each new year New column = schema change Aggregating across years = complex

✓ Solution — Year as a dimension column

CREATE TABLE fct_district_month (
    district_id   INT,
    year_month    DATE,  -- 2022-03-01
    permit_count  INT,
    PRIMARY KEY (district_id, year_month)
);

-- New month = new ROW, not new column.
New period = INSERT, not ALTER TABLE Any date range query is trivial

🔍 How to recognize Metadata Tribbles

  • "We need a table per [data value]..."
  • "We forgot to create the new year's table."
  • "How do I query a table name dynamically?"
  • "How do I search many tables at once? They all have the same columns."
  • "Adding a column means I have to update 5 tables."

Solutions for large tables

✓ Horizontal partitioning (rows)

CREATE TABLE Permits (
    permit_id   SERIAL PRIMARY KEY,
    issue_date  DATE
) PARTITION BY HASH (
    EXTRACT(YEAR FROM issue_date)
) PARTITIONS 4;
-- Still one logical table.
-- DB manages physical split.

Use when: table grows very large and queries are mostly date-filtered. The partition is invisible to SQL — you still query Permits, not Permits_2022.

✓ Vertical partitioning (columns)

-- Main table: lean, fixed-width cols
CREATE TABLE Permits (
    permit_id   SERIAL PRIMARY KEY,
    issue_date  DATE,
    district_id INT
);

-- Dependent table: bulky/rare columns
CREATE TABLE PermitDetails (
    permit_id   INT PRIMARY KEY
        REFERENCES Permits(permit_id),
    description TEXT   -- rarely queried
);

Use when: some columns are very large (TEXT, BLOB) and rarely needed. Keeps the main table fast for the 90% of queries that don't need the bulky data.

Chapter 11 — 31 Flavors Antipattern

Objective: restrict a column to a known set of valid values. Mistaken approach: encode those values in the column definition itself.

✗ Antipattern — Values baked into schema

-- CHECK constraint
CREATE TABLE Permits (
    permittype VARCHAR(20)
        CHECK (permittype IN (
            'BUILDING',
            'ELECTRICAL',
            'PLUMBING'
        ))
);

-- Or ENUM (MySQL)
CREATE TABLE Permits (
    permittype ENUM(
        'BUILDING',
        'ELECTRICAL',
        'PLUMBING'
    )
);
New value = ALTER TABLE + possible downtime Retiring old value = historical data problem Querying valid values = parse INFORMATION_SCHEMA App code list drifts out of sync Not portable across DB brands

✓ Solution — Lookup table with FK

CREATE TABLE PermitTypes (
    permittype  VARCHAR(50) PRIMARY KEY,
    active      BOOLEAN NOT NULL DEFAULT TRUE,
    notes       TEXT
);

INSERT INTO PermitTypes VALUES
    ('BUILDING', TRUE, NULL),
    ('ELECTRICAL', TRUE, NULL),
    ('PLUMBING', TRUE, NULL);

CREATE TABLE Permits (
    permit_id   SERIAL PRIMARY KEY,
    permittype  VARCHAR(50),
    FOREIGN KEY (permittype)
        REFERENCES PermitTypes(permittype)
        ON UPDATE CASCADE
);
New value = INSERT (no DDL) Retire value = SET active = FALSE Query valid values = simple SELECT No app code sync problem

The "Adding a New Flavor" problem in detail

✗ Adding a value with ENUM

-- Must redefine the entire column.
-- Some DBs require ETL (dump → redefine → reload).
ALTER TABLE Permits
MODIFY COLUMN permittype
    ENUM('BUILDING', 'ELECTRICAL',
         'PLUMBING', 'NEW_TYPE');
-- Risk: table locked during ALTER.
-- Risk: you must know the current list exactly.

✓ Adding a value with lookup table

-- One row. No DDL. No downtime.
INSERT INTO PermitTypes (permittype)
    VALUES ('NEW_TYPE');

-- Done. The FK now accepts the new value.

✗ Retiring an old value

-- Remove 'PLUMBING' from ENUM:
ALTER TABLE Permits
MODIFY COLUMN permittype
    ENUM('BUILDING', 'ELECTRICAL');
-- Problem: what happens to rows where
-- permittype = 'PLUMBING'?
-- Historical data is now broken.

✓ Retiring an old value

-- Soft-delete: mark inactive.
UPDATE PermitTypes
SET active = FALSE
WHERE permittype = 'PLUMBING';

-- Historical rows still have a valid FK.
-- Active UI only shows active values:
SELECT permittype FROM PermitTypes
WHERE active = TRUE;

🔍 How to recognize 31 Flavors

  • "We have to take the database offline to add a new choice to the menu."
  • "The status column can only have these values — we shouldn't need to revise this list." (Shouldn't need to ≠ can't.)
  • "The list in the application code got out of sync with the database — again."
  • "How do I get the list of valid values for this column?" (Answer: parse INFORMATION_SCHEMA. Red flag.)

Extension: SCD Type 2 for lookup tables (beyond Karwin)

When the valid value itself changes over time and you need to track history (e.g., a FIPS county code gets reassigned), the lookup table can be extended to SCD Type 2:

CREATE TABLE CountyFIPS (
    surrogate_id  SERIAL PRIMARY KEY,  -- stable internal key
    fips_code     VARCHAR(5),          -- the business key (may change)
    county_name   TEXT,
    valid_from    DATE NOT NULL,
    valid_to      DATE,                -- NULL = currently active
    active        BOOLEAN NOT NULL DEFAULT TRUE
);

This handles the case where fips_code = '42001' is reassigned: the old row gets a valid_to date and active = FALSE; the new mapping gets a new row. Historical permit records joined via surrogate_id still resolve correctly.

-- Wrong: CHECK (permittype IN ('BUILDING', ...))        -- same problem
