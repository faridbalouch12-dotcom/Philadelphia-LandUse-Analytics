Lookup Tables vs SCD Type 2 — What's the Difference?

Sources: Kimball Ch. 2 (pp. 40, 53–55) · SQL Antipatterns Ch. 11 (31 Flavors) · Zoning window decision memo

These two patterns are often confused because they both involve a separate table that holds a set of valid values, and both are used in dimensional warehouses. But they solve completely different problems. Confusing them produces either an over-engineered dimension that doesn't need history, or a fragile constraint that breaks when data changes.

"Dimensions provide the 'who, what, where, when, why, and how' context surrounding a business process event." — Kimball, p. 40

"Use metadata when validating against a fixed set of values. Use data when validating against a fluid set of values." — Karwin, SQL Antipatterns Ch. 11

2. What Kimball Actually Says About SCD Type 2

From Kimball Ch. 2, p. 54 (emphasis added):

"Type 2 changes add a new row in the dimension with the updated attribute values. This requires generalizing the primary key of the dimension beyond the natural or durable key because there will potentially be multiple dimension rows describing each member. When a new row is created for a dimension member, a new primary surrogate key is assigned and used as a foreign key in all fact tables from the moment of the update until a subsequent change creates a new dimension key and updated dimension row."

Three required columns are added to every Type 2 dimension row:

  1. row_effective_date — when this version of the row became active
  2. row_expiration_date — when it was superseded (NULL = current)
  3. current_row_indicator — boolean flag for the active version

This is complex machinery. It only makes sense when you have a real entity with changing descriptive attributes — like a customer who moves cities, or an employee who changes departments.

What SCD Type 2 is NOT for

SCD Type 2 is for entities whose descriptive attributes change. It is not for validating which values are currently permitted. It is not for tracking measurements. If you reach for Type 2 and you're not tracking an entity's changing profile, you're probably using the wrong tool.

3. What the 31 Flavors Antipattern Says

From Karwin, SQL Antipatterns Ch. 11: The mistake is encoding valid values in the column definition itself — baking data into schema.

-- ANTIPATTERN: valid values baked into CHECK constraint
CREATE TABLE Permits (
    permittype VARCHAR(20)
        CHECK (permittype IN ('BUILDING', 'ELECTRICAL', 'PLUMBING'))
);

-- ANTIPATTERN: ENUM bakes values into schema
CREATE TABLE Permits (
    permittype ENUM('BUILDING', 'ELECTRICAL', 'PLUMBING')
);

The problem: when new values appear, you need a DDL operation — ALTER TABLE — to update the constraint. In some databases this locks the table. In all cases, it means data values are controlling your schema structure.

The correct fix: lookup table with FK

-- CORRECT: valid values are rows in a reference table
CREATE TABLE ZoningCodes (
    zoning_code      VARCHAR(20) PRIMARY KEY,
    code_description TEXT       NOT NULL,
    broad_category   VARCHAR(50),
    active           BOOLEAN    NOT NULL DEFAULT TRUE
);

-- Adding a new zoning code: just INSERT — no DDL, no downtime
INSERT INTO ZoningCodes VALUES ('CMX-5', 'Community Commercial Mixed-Use 5', 'Commercial', TRUE);

-- Retiring an old code: UPDATE — historical rows still valid
UPDATE ZoningCodes SET active = FALSE WHERE zoning_code = 'OLD-CODE';

Karwin's rule: "Use metadata when validating against a fixed set of values. Use data when validating against a fluid set of values." Zoning codes are fluid — Philadelphia can add, rename, or retire them at any time. So they belong as rows, not in schema objects.

4. The Confusion: Where These Get Conflated

The confusion happens when someone asks: "Zoning codes can change year to year — shouldn't I track that with SCD Type 2?"

This sounds reasonable but mixes up two different questions:

Question What's actually changing Correct pattern
"What does RSA-5 mean?" The code's description (stable — RSA-5 means the same thing in 2019 and 2025) Lookup table (static)
"Which polygons are classified RSA-5 this year vs last year?" Which land areas carry the RSA-5 label — a measurement, not a description Periodic snapshot fact table
"Did Philadelphia rename RSA-4 to RSA-5 between vintages?" The code vocabulary used in different source vintages Crosswalk table (pipeline layer)
"RSA-5's meaning changed — I need to track the old and new definition" The dimension entity's attributes changed over time SCD Type 2 (only if this actually happens)
The key test: Is what's changing a descriptive attribute of an entity (→ SCD Type 2), or is it a measurement of how much of something exists (→ fact table), or is it which values are permitted (→ lookup table)?

5. Why SCD Type 2 Was Rejected for Zoning Codes

Kimball is explicit (p. 40): "Dimensions provide the descriptive context surrounding a business process event." They describe — they do not measure.

For dim_zoning_code, the question is: does the code's descriptive context change in a way that requires historical tracking?

  • RSA-5 means "Residential Single Family Attached, density 5" — this is stable across vintages.
  • The amount of land classified as RSA-5 changes year to year — but that's a measurement, not a dimension attribute.
  • Measurements belong in fact tables (fct_district_year_zoning_composition), not dimensions.
The error: Treating "zoning composition changed" as "the zoning code dimension changed." These are different things. Composition change → fact table. Attribute change → SCD Type 2. Code vocabulary change across source vintages → crosswalk in the pipeline. 
-- WRONG: SCD Type 2 for zoning codes
SELECT zoning_code, code_description, row_effective_date, row_expiry_date
FROM dim_zoning_code
WHERE current_row = TRUE;
-- This tracks when RSA-5's *description* changed. That almost never happens.
-- And it still doesn't tell you how much land is RSA-5 this year vs last year.

-- CORRECT: static lookup + periodic snapshot fact
SELECT f.vintage_year, f.district_id, f.zoning_code,
       d.code_description, d.broad_category,
       f.pct_district_area
FROM fct_district_year_zoning_composition f
JOIN dim_zoning_code d ON f.zoning_code = d.zoning_code
WHERE f.district_id = 'D09'
ORDER BY f.vintage_year, f.pct_district_area DESC;
-- dim_zoning_code provides static descriptive context.
-- The fact table provides the measurement that changes year to year.

6. The Crosswalk: A Third Pattern That Isn't Either

When extending the zoning window to earlier vintages, a code naming difference may appear — e.g., the 2019 dataset uses RSA-4 for what 2021+ calls RSA-5. This is neither a lookup table concern nor an SCD Type 2 concern. It's a pipeline crosswalk:

-- Crosswalk table: lives in the pipeline/staging layer, NOT in the warehouse
CREATE TABLE stg_zoning_code_crosswalk (
    source_code     VARCHAR(20),   -- code as it appears in the vintage file
    vintage_year    INTEGER,        -- which source vintage uses this name
    canonical_code  VARCHAR(20),   -- normalized code loaded into the warehouse
    notes           TEXT
);

-- Example: 2019 used 'RSA-4' for what became 'RSA-5' in 2021+
INSERT INTO stg_zoning_code_crosswalk VALUES
    ('RSA-4', 2019, 'RSA-5', 'Renamed in 2021 code revision');

The warehouse always sees RSA-5. The crosswalk is applied during the load step — it never appears in the presentation layer. This is how you extend the vintage window without rewriting metric queries.

Three-layer separation:
Pipeline → crosswalk normalizes code vocabulary across source vintages
Warehouse dim → lookup table provides stable descriptive context per code
Warehouse fact → periodic snapshot measures land area share per code per district per year

7. Decision Flowchart

You have a set of values (e.g., zoning codes, permit types) that appear in your data. Which pattern do you use?
Q1: Do you need to validate which values are currently permitted and provide descriptions for them?
YES →
Lookup table with FK constraint

One row per valid code. Add new codes with INSERT. Retire with active = FALSE.

NO ↓
Q2: Does the entity have descriptive attributes that change over time, and do you need to report historical facts under the old profile?
YES →
SCD Type 2 dimension — add new row per change with effective/expiry dates

E.g., a customer moved from Philadelphia to Pittsburgh — sales before the move belong to Philly, after to Pittsburgh.

NO ↓
Q3: Are you measuring how much of something exists at regular time intervals?
YES →
Periodic snapshot fact table — one row per entity per time period

E.g., what share of district D09 is zoned RSA-5 in each vintage year?

NO ↓
Q4: Are you normalizing code names that differ across source vintages?
YES →
Crosswalk table in the pipeline/staging layer — not a warehouse construct

Applied at load time; warehouse never sees the old vocabulary.
