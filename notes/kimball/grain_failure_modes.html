Grain Failure Modes

Philadelphia Data Warehouse — Task 11.1 reference | Source: Kimball & Ross, The Data Warehouse Toolkit (B1)

What is grain?
Grain is the row-level contract of a table — it defines exactly what one row represents. A precise grain statement locks in: (1) the unit of uniqueness, and (2) the type of fact being stored. Grain violations cause silent query errors — counts inflate, averages skew, and joins fan out, all without raising an error.
---

FM1 — Grain Integrity Failure

Occurs when duplicate rows violate the primary key guarantee. The grain statement says "one row = one thing," but multiple rows exist for the same thing.

Example: fct_permits

Grain: one issued permit event per permitnumber

Broken — duplicate permitnumber
permitnumberstatuspermitissuedatepermittype
P-100432Issued2023-03-15Building
P-100432Issued2023-03-15Building
P-100433Issued2023-03-18Zoning

Result: COUNT(*) = 3 but only 2 permits exist. Every district-level count is now inflated. No error is raised.

Fixed — deduplication enforced in staging
permitnumberstatuspermitissuedatepermittype
P-100432Issued2023-03-15Building
P-100433Issued2023-03-18Zoning
Fix: Deduplicate on permitnumber in the staging layer before loading into fct_permits. Log any dropped duplicates for audit.

FM2 — Mixed-Grain Facts

Occurs when two different types of facts — representing different business questions — are stored in the same table under the same grain. The rows look identical structurally, but they answer fundamentally different questions.

Example: fct_district_year_zoning_composition

Grain: one planning district × one vintage year × one zoning code composition snapshot

Broken — snapshot + change metric mixed
district_idvintage_yearzoning_codearea_sqmipct_districtpct_change_from_prior_year
D012020RM12.110.5%NULL — no prior year
D012021RM12.311.5%+9.5%
D012022RM12.412.0%+4.3%

Problems: (1) 2020 row is structurally incomplete — pct_change_from_prior_year is always NULL for the earliest vintage. (2) The table now answers two questions simultaneously: "What exists?" and "How did it change?" These are different business processes stored at the same grain. Analysts querying composition now have to mentally filter out the change column, and vice versa.

Fixed — two separate tables, each with a clean grain
TableGrainColumnsAnswers
fct_district_year_zoning_compositiondistrict × year × zoning_codearea_sqmi, pct_district"What is the composition in year Y?"
Analyst self-join or agg_zoning_yoy_change (if pre-built)district × year × zoning_codepct_change_from_prior_year"How did it change from Y-1 to Y?"
Fix: Keep fct_district_year_zoning_composition as a pure snapshot. Year-over-year change is computed at query time via a self-join (or a separate aggregation table if pre-computation is needed). This keeps every row in the snapshot table structurally complete and unambiguous.
---

Why This Matters

Key principle

Grain failures are silent. Queries run. Results are returned. No errors are raised. The only signal is a number that's slightly off — which you may never notice without a known-good benchmark to compare against.

This is why grain is declared before implementation: once data is loaded with a broken grain, every downstream metric that touched it is suspect.
