Why this matters for the lookup table: If historical extension beyond 2021 is attempted, HANSEN values must be added as separate rows in permit_category_groups, each mapped to the same canonical group as their ECLIPSE equivalent. The lookup table handles this gracefully — no schema change required, just new rows. Without this mapping, a query spanning eras would show e.g. "ZP_ZONING" and "ZONING/USE REGISTRATION" as two separate category buckets in the composition metric — doubling apparent zoning activity.

The 3 Category Grouping Risks

R1 — Value Emergence
New permittype values appear mid-pipeline
The city introduces a new permit type in the source system. If categories are hardcoded as ENUM or CHECK constraints, ingestion throws an error and the pipeline stops. If the new value is simply unhandled, permits silently disappear from counts — no error, no warning, just missing data in the composition metric.
Mitigation: Lookup table with Unmapped/Other catch-all. Every unknown value is captured, not dropped. Monitor unmapped share per monthly load; alert if > 1%. Update lookup table when new values are confirmed.
Likelihood: Low (5-yr ECLIPSE window is stable). Impact: High if unhandled.
R2 — Cross-Era Label Mismatch
HANSEN → ECLIPSE transition creates phantom category splits
The same real-world permit type is labeled differently across source system eras. "ZP_ZONING" (HANSEN) and "ZONING/USE REGISTRATION" (ECLIPSE) describe the same thing. Without explicit cross-era mapping, they appear as two separate categories — artificially splitting composition and inflating category counts in any cross-era query.
Mitigation: Document known cross-era label pairs. Apply canonical mapping in staging before any cross-era join. The lookup table accepts both raw values as separate rows pointing to the same canonical group.
Unlike R3, this is a known, one-time, documented transition — not ongoing drift. Low risk for MVP (5-yr window is 100% ECLIPSE).
R3 — Silent Label Drift
Incremental typeofwork relabeling creates phantom trends
Unlike the HANSEN→ECLIPSE transition (documented, one-time), typeofwork label drift happens silently and continuously with no announcement. "Alterations" becomes "Addition/Alteration" — same real-world activity, different string. Composition charts show a new category appearing and an old one shrinking. It looks like a real trend in building activity, but it is just relabeling.
Mitigation: Exclude typeofwork from primary MVP grouping entirely. If introduced in a later phase: unmapped catch-all + monthly drift monitoring. Compare typeofwork distribution year-over-year to detect relabeling events.
Unlike R2, this is continuous, undocumented, and unannounced — the hardest type of drift to catch without monitoring.
