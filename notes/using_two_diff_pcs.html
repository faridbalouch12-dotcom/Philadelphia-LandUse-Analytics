2. The Same Point in Two Coordinate Systems

Philadelphia City Hall sits at approximately 39.9526° N, 75.1652° W in GCS. Here's what that same physical location looks like in the two PCS systems:

In EPSG:2272: (2,694,521 ft, 236,811 ft)

In EPSG:32618: (487,462 m, 4,422,977 m)

The insight: These two rows of numbers describe the exact same physical point on Earth. But if PostGIS thinks both layers are in the same CRS when they're not, it will treat (2,694,521, 236,811) and (487,462, 4,422,977) as points in completely different locations — one is in Philadelphia, the other would plot somewhere in the middle of the Atlantic Ocean.

3. What Happens During a Spatial Join With Mismatched CRS

Correct: Same CRS

Both layers in EPSG:2272 — geometries overlap where they should.

Broken: Mismatched CRS

District in EPSG:2272, census tract stored as EPSG:32618 but not declared — PostGIS reads the UTM coordinates as if they're State Plane feet. The geometry lands in the wrong place entirely.

4. Why This is Dangerous — Silent Failures

Worst case scenario: A CRS mismatch doesn't always throw an error. If both layers are stored without a declared SRID in PostGIS, PostGIS may happily run the spatial join and return 0 rows — or worse, return partially wrong rows with no warning. You'd only notice if you checked the output count against expectations.

There are three failure modes:

Failure ModeWhat HappensHow You'd Notice
Hard errorPostGIS refuses to run: "Operation on mixed SRID geometries"Query fails with error — easy to catch
Silent zeroNo overlap found, join returns 0 rowsCheck: are all permits unassigned?
Silent wrongNo SRID declared, PostGIS treats both as same — geometry mismatch causes random/partial resultsHardest to catch — spot-check known addresses

5. The Fix — ST_Transform()

Before any spatial join, reproject all layers to a common CRS using PostGIS's ST_Transform():

-- Assign a permit to its planning district -- Both layers must be in the same CRS first SELECT p.permit_id, d.district_id FROM permits p JOIN planning_districts d ON ST_Within( ST_Transform(p.geom, 2272), -- reproject permit point to EPSG:2272 ST_Transform(d.geom, 2272) -- reproject district polygon to EPSG:2272 )
Project convention: Store geometries in their source CRS, always reproject to EPSG:2272 at query time using ST_Transform(). This keeps raw data clean while ensuring all spatial operations use consistent linear units.
